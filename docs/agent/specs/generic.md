## 0. Group-wide findings (GG1–GG8)

**GG1. Two different "UI paths" exist, and neither goes through `INotationInteraction` for properties.**
`INotationInteraction` has no property-setting method (`src/notation/inotationinteraction.h`, only
`toggleVisible()` at :54). The Properties panel (Inspector) edits elements directly: it holds raw
`EngravingItem*` from the selection, opens a command on `INotationUndoStack`
(`aim.cpp:867-876` → `prepareChanges`), calls `EngravingItem::undoChangeProperty`
(`aim.cpp:492`), notifies `notationChanged` (`aim.cpp:908-915`, called at `aim.cpp:495`
*before* `commitChanges` at `aim.cpp:496`/`881`). So for set_property the "same code path as
the UI" is `EngravingItem::undoChangeProperty`, not an interaction method. CLAUDE.md rule 4
("drop to Score only where the UI does the same") is satisfied because the Inspector itself does
this.

**GG2. Nested transaction calls in this group collapse safely under the lock.**
`AbstractInspectorModel::beginCommand/endCommand` call `prepareChanges/commitChanges`
(`aim.cpp:867-885`), which are no-ops while locked (notes-G1). `NotationInteraction::startEdit/apply`
(`ni.cpp:314-330`) likewise; `apply()` still notifies `notationChanged` (`ni.cpp:328`), which is
harmless. `undoChangeProperty`, `Score::cmdDeleteSelection`, `Score::deleteItem` and
`Score::select*` never call `startCmd/endCmd` themselves (no hits in the engraving-wide grep:
the only nested `startCmd/endCmd` in `src/engraving/{dom,editing}` are in figuredbass.cpp:749-771,
lyrics.cpp:185-218, playcounttext.cpp:53-56, tiejumppointlist.cpp:210-217, unrollrepeats.cpp:101-114,
cmd.cpp:2909-2913, edit.cpp:2065-2168, 2217-2287, 2301-2315, 4590-4592, 7980-8162,
textedit.cpp:264, 641, 925-996).

**GG3. Hazards that bypass the core's rollback, reached from this group.**
- `checkAndShowError()` (dialog + clears `MScore::_error`, structure-G2) is reached by
  `NotationInteraction::deleteSelection` (`ni.cpp:5448`) and by many `cmd` targets (listed in
  the cmd section). Never call those wrappers.
- `activeCommand()->unwind()` (structure-G3) is reached by `remove` on a `TIMESIG`
  (`edit.cpp:2775` → `cmdRemoveTimeSig` → `edit.cpp:1663-1664`).
- `MScore::setError` with a non-warning error makes `endCmd` roll back the **whole** outer
  transaction (`cmd.cpp:418-424`; `setError` defaults to `warning=false`,
  `src/engraving/dom/mscore.h:234`). Reached by `remove` on the first key signature
  (`edit.cpp:4082`) and by `cmdFlip` on empty selection (`edit.cpp:2453`).

**GG4. Non-undoable side mutations inside undoable helpers.** These happen outside the undo
stack and are not reverted by rollback; all are layout-cache or flag updates, listed so the
reviewer is not surprised:
`eo.cpp:456-458` (PLACEMENT/HAIRPIN_TYPE resets styled OFFSET with `setProperty`),
`spanner.cpp:1663-1668` (Spanner PLACEMENT resets segment offsets with `setOffset`),
`bracket.cpp:318-320` (Bracket COLOR `setColor`), `clef.cpp:369-371` (`setGenerated(false)`),
`edit.cpp:4655-4658` (generated beam deleted with `delete`, regenerated by layout).

**GG5. Linked-part propagation is per-property, not per-element.**
`changeProperties` (`eo.cpp:398-427`) walks `linkListForPropertyPropagation()` and asks
`EngravingItem::propertyPropagation` (`ei.cpp:1469-1530`):
- Pids with `link=true` in the property table always propagate (`ei.cpp:1473-1475`; table
  column `prop.cpp:44-51`, e.g. PITCH/TPC1/TPC2 `prop.cpp:73-77`).
- Pids in `PropertyGroup::NONE` never propagate to linked items (`ei.cpp:1477-1479`).
- Same score (linked staves): VISIBLE, COLOR and POSITION-group Pids stay independent per staff
  (`ei.cpp:1486-1498`).
- From the master: propagate only if the part item is still linked to master for that group
  (`ei.cpp:1525-1529`); a system object propagates only from the top system object
  (`ei.cpp:1520-1523`).
- **From a part (excerpt): never propagates; instead the part item is unlinked from master for
  that group** (`ei.cpp:1514-1518`, `ei.cpp:2656-2663`, undoable `ChangeProperty` on
  POSITION_/APPEARANCE_LINKED_TO_MASTER). TEXT-group Pids follow TEXT_LINKED_TO_MASTER
  (`ei.cpp:1501-1512`).
Consequence: set_property on a master element is the "edit everywhere" case; set_property on a
part element is "override in this part only". The handle must say which score it lives in
(notes-G7, structure-G4 recommend master for edits; for set_property the part case is a real,
distinct user intent).
Measure-level Pids do not reach unlinked part measures (structure-G5); `deleteItem` itself loops
`scoreList()` for REPEAT_START/END (`edit.cpp:3032-3049`).

**GG6. Unknown Pids bubble up to the parent.** `EngravingItem::getProperty` and `setProperty`
forward any Pid they do not handle to `explicitParent()` (`ei.cpp:1173-1178`, `ei.cpp:1255-1261`).
So `getProperty(pid).isValid()` does **not** prove the element owns the property: a NOTE
answers Chord, Segment and Measure Pids. A `ChangeProperty` recorded on the note will then write
the parent's property on redo (`src/engraving/editing/editproperty.cpp:39-55`). Validation must
use an explicit per-element-type Pid allow-list, not `isValid()`.

**GG7. Selection is per `Score` object, and the user sees the current notation's score.**
`Score::select*` writes `Score::m_selection` (`score.cpp:3349-3416`). The view repaints and the
Inspector and note-input state refresh only on `INotationInteraction::selectionChanged()`
(`src/notationscene/qml/MuseScore/NotationScene/abstractnotationpaintview.cpp:280-282`,
`src/inspector/qml/MuseScore/Inspector/inspectorlistmodel.cpp:371`,
`src/notation/internal/notationnoteinput.cpp:76-87`). That notification is emitted by
`NotationInteraction::notifyAboutSelectionChangedIfNeed` (`ni.cpp:369-380`, private,
`src/notation/internal/notationinteraction.h:383`) when `Score::selectionChanged()` is set, which
public `select`, `selectAll`, `clearSelection` call (`ni.cpp:995`, `1091`, `1142`) and which runs
after every `commitChanges` via `stackChanged` (`ni.cpp:255-258`;
`src/notation/internal/notationundostack.cpp:142-145`). `rollbackChanges` does **not** emit
`stackChanged` (`notationundostack.cpp:119-130`).

**GG8. `UndoMacro` snapshots and restores the selection and input state.** The macro opened by
`prepareChanges` records selection + `InputState` (`src/engraving/editing/undo.cpp:544-548`) and
restores them on undo/redo (`undo.cpp:550-580`). Selection changes themselves are never undo
commands, so a request that only changes the selection leaves an empty macro, which `endCmd`
discards (notes-G1).

### set_property  ·  command://notation/set_property

**UI entry point.**
Properties panel (Inspector). Every property row is a `PropertyItem` built by
`AbstractInspectorModel::buildPropertyItem` (`aim.cpp:713-750`) whose default setter is
`onPropertyValueChanged` (`aim.cpp:749` → `aim.cpp:465-469`) → `setPropertyValue(items, pid, value)`
(`aim.cpp:471-497`):
1. `beginCommand("Edit <propertyUserName>")` (`aim.cpp:478`, `867-876`).
2. For each item: `ps = item->propertyFlags(pid)`; if `STYLED` then `UNSTYLED` (`aim.cpp:485-489`).
3. `propValue = valueToElementUnits(pid, value, item)` (`aim.cpp:491`, `613-662`).
4. `item->undoChangeProperty(pid, propValue, ps)` (`aim.cpp:492`).
5. `updateNotation()` → `notationChanged().notify()` (`aim.cpp:495`, `908-915`); `endCommand()`
   → `commitChanges` (`aim.cpp:496`, `878-885`).
Reset ("reset to default" button) is `resetPropertyValue` → `undoResetProperty` (`aim.cpp:505-523`,
`eo.cpp:359-366`), which writes `propertyDefault(pid)` with flag `STYLED`.

Engraving: `EngravingObject::undoChangeProperty(id, v, ps)` (`eo.cpp:438-498`): early return if
value and flag already equal (`eo.cpp:440-442`); special cases for PLACEMENT/HAIRPIN_TYPE
(`eo.cpp:443-459`), TEXT_STYLE (expands into every styled Pid of the new style, `eo.cpp:460-471`),
OFFSET (`eo.cpp:472-479`), EXCLUDE_FROM_OTHER_PARTS (`manageExclusionFromParts`, `eo.cpp:480-488`),
VOICE_ASSIGNMENT (also sets VOICE 0, `eo.cpp:489-493`); then `changeProperties` (`eo.cpp:494`) and
clears GENERATED (`eo.cpp:495-497`). `changeProperty` records `ChangeProperty` (or
`ChangeBracketProperty` for bracket items) only when value or flag differ (`eo.cpp:382-392`).

Inspector-specific setters that do **not** use the default path (from the custom-lambda list,
`git grep "build(PointF)?PropertyItem(...Pid::X, ["` in `src/inspector`):
- VISIBLE (General section): `Score::undoChangeVisible(item, v)` per item
  (`general/generalsettingsmodel.cpp:50-52`, `159-175`; `edit.cpp:6669-6686`), which routes notes,
  rests, ornaments and trill segments to dedicated helpers.
- SMALL: applied to the parent CHORD when the item is inside a chord
  (`general/generalsettingsmodel.cpp:54-56`, `84-90`).
- OFFSET (Appearance): applied to the parent CHORD for NOTE/STEM/HOOK
  (`general/appearance/appearancesettingsmodel.cpp:59-65`, `84-110`).
- Spanners: the Inspector replaces every selected spanner segment by its Spanner for all line
  models (`ers.cpp:91-111`, `312-358`), but the Appearance section keeps the raw segments
  (`appearancesettingsmodel.cpp:76-82`), so OFFSET goes to a segment and everything else to the
  spanner.
- STEM_DIRECTION on a stem: applied to the beam if the chord is beamed, else to the stem

- VOICE: first VOICE_ASSIGNMENT=CURRENT_VOICE_ONLY, then VOICE

**Selection set-up.** None for the default path: the Inspector already holds the item pointers.
Exception: HAS_PARENTHESES (selection-driven, above); recommend not exposing it in v1.

**Arguments.**
```json
{
  "type": "object",
  "required": ["handle", "property", "value"],
  "properties": {
    "handle":   { "$ref": "#/defs/handle" },
    "property": { "type": "string", "description": "C++ Pid identifier, e.g. PLACEMENT" },
    "value":    { "description": "typed by the Pid's P_TYPE, see table; null = reset to style default" },
    "segment":  { "type": "integer", "minimum": 0, "description": "spanner segment index; only for segment Pids (OFFSET, OFFSET2, USER_MODIFIED); requires a laid-out spanner" }
  }
}
```
Property names: the C++ Pid identifier, as the assessment proposes. Verified reason, stronger
than stated: 14 Pids share the XML name `"subtype"` (`prop.cpp:60, 102, 137, 172, 187, 189, 190,
193, 199, 221, 242, 428, 429, 432`), and `"color"`, `"velocity"`, `"anchor"`, `"size"`, `"text"`,
`"align"` are also duplicated (`prop.cpp:63/313, 84/206, 85/258, 139/330, 156/222, 343/344`);
four Pids have an empty XML name (`prop.cpp:508-511`). `propertyId(name)` returns the first match
(`prop.cpp:533-541`). The registry must carry its own name→Pid table.

Value typing, mirroring `valueToElementUnits` (`aim.cpp:613-662`), not the plugin API:
| P_TYPE (`src/engraving/types/propertyvalue.h:41-135`) | JSON | Conversion |
|---|---|---|
| BOOL | boolean | direct |
| INT (plain number) | integer | direct, with per-Pid range |
| REAL | number | direct |
| STRING | string | direct |
| SPATIUM | number (sp) | `Spatium(v)` (`aim.cpp:637-638`) |
| MILLIMETRE | number (sp) | `Spatium(v).toMM(item->spatium())` (`aim.cpp:634-635`) |
| POINT | `{x, y}` (sp) | × `spatium()` if `offsetIsSpatiumDependent()`/`sizeIsSpatiumDependent()`, else × `DPMM` (`aim.cpp:626-632`) |

`PropertyValue::fromQVariant` casts integers to enums with no range check
(`propertyvalue.cpp:253-311`), so every enum and integer must be range-checked before mutation.

Plugin-API divergence (do not copy): `ScoreElement::set` (`src/engraving/api/v1/scoreelement.cpp:162-227`)
multiplies every POINT by spatium regardless of `offsetIsSpatiumDependent` (`:201-203`), does not
map segments to spanners, does not convert VERSE, and for TIMESIG_ACTUAL calls
`Measure::adjustToLen` (`:180-188`). Its flag logic (`:218-219`) is equivalent to the Inspector's.

**Proposed Pid exposure (v1).** Expose the Pids the Inspector exposes (218 distinct Pid tokens appear
in `buildPropertyItem`/`buildPointFPropertyItem` calls under `src/inspector`; two are placeholders, not
edited properties: `Pid::END` at `notation/lines/pedalsettingsmodel.cpp:94` and
`Pid::DURATION_TYPE_WITH_DOTS` at `notation/beams/beammodesmodel.cpp:35`), as a per-element-type
table generated from the Inspector models (each model's `createProperties()` names its Pids and
its `requestElements()` names the element type). Route as follows:
- Default path (`undoChangeProperty` + STYLED→UNSTYLED + unit conversion): everything not listed below.
- Special routes: VISIBLE → `Score::undoChangeVisible`; SMALL → chord for chord children;
  OFFSET → chord for NOTE/STEM/HOOK, segment for spanners; STEM_DIRECTION on stem → beam or stem;
  VOICE → VOICE_ASSIGNMENT then VOICE; VERSE → value − 1.
- Refuse in v1 (map to E_PROPERTY_READONLY or point to the owning command):
  structural Pids TICK, TRACK, SPANNER_TICK, SPANNER_TICKS, SPANNER_TRACK2, DURATION,
  DURATION_TYPE_WITH_DOTS, TIMESIG, TIMESIG_ACTUAL, TIMESIG_STRETCH, LYRIC_TICKS, KEY, KEY_CONCERT,
  GAP (`prop.h:247-303, 425-433`) — these change score structure and have dedicated commands;
  PITCH, TPC1, TPC2, LINE, FRET, STRING (`pitch` group); TEXT (`text` group, XML text);
  BARLINE_TYPE, REPEAT_START/END, REPEAT_COUNT (`structure` group; `deleteItem` shows the
  part-loop these need, `edit.cpp:3032-3049`); SELECTED, GENERATED (internal flags,
  `prop.cpp:61-62`); enum-in-INT Pids and SUBTYPE (type changes; not exposed by the Inspector
  except OTTAVA_TYPE); HAS_PARENTHESES (selection-driven route).
- `null` value → reset via `undoResetProperty` (`eo.cpp:359-366`), which is the Inspector's reset.

**Validation before mutation.**
| Check | Error |
|---|---|
| handle resolves to a live element (re-validated, CLAUDE.md rule 2) | E_STALE_HANDLE |
| property name in the registry table | E_UNKNOWN_PROPERTY |
| Pid allowed for this element type (explicit table, GG6) | E_PROPERTY_NOT_APPLICABLE |
| Pid not in the refuse list | E_PROPERTY_READONLY |
| value parses for the Pid's P_TYPE; enum round-trips; integer/real in range | E_VALUE_TYPE / E_RANGE |
| BEAM_MODE on a chord/rest whose duration cannot take it (`chordrest.cpp:671-680`) | E_NO_EFFECT (pre-checked, since the override returns silently) |
| BEAM_CROSS_STAFF_MOVE: `acceptCrossStaffMove(v)` (`beambase.cpp:46-49`) | E_RANGE |
| `segment` given only for segment Pids, index < `spannerSegments().size()` | E_RANGE |
| not in text edit / note input (notes-G6) | E_BUSY |

**Post-condition.** Re-read `item->getProperty(pid)` and `propertyFlags(pid)` on the target the
route chose (chord, beam, spanner, segment) and compare with the converted value; for TEXT_STYLE
compare the TEXT_STYLE value only (it rewrites other Pids, `eo.cpp:460-471`). Equality before the
call means the request is a no-op (`eo.cpp:440-442`); report "unchanged" rather than an error.

**Nested commands.** None. `undoChangeProperty` and the special routes push undo commands into
the active macro (notes-G1); no `startCmd/endCmd`, no dialogs, no `MScore::setError` in these
paths (GG2).

**Linked parts / excerpts.** Propagates by the rules in GG5, inside `undoChangeProperty`.
Editing a part element unlinks that property group from the master instead of propagating
(`ei.cpp:1514-1518`). Character text Pids have their own propagation loop (`textbase.cpp:3401-3422`).

**Crash and corruption risks.**
- Unknown Pids are forwarded to parents (GG6): a wrong Pid on a note can silently change the
  measure.
- Out-of-range enum integers are accepted by `fromQVariant` (`propertyvalue.cpp:253-311`).
- `EXCLUDE_FROM_OTHER_PARTS` adds/removes linked copies in parts (`eo.cpp:480-488`); exercised by
  `parts_tests.cpp:1151` (`partExclusion`).
- TEXT_STYLE rewrites every styled Pid of the new style (`eo.cpp:460-471`).
- GG4 side mutations are not rolled back.

**Existing upstream tests.**
`src/engraving/tests/parts_tests.cpp:1151` (partExclusion), `:1210` (partPropertyLinking: PLACEMENT,
MUSICAL_SYMBOLS_SCALE, *_LINKED_TO_MASTER), `textbase_tests.cpp:142` (FONT_STYLE),
`:180` (FONT_SIZE), `note_tests.cpp:345` (SHOW_STEM_SLASH), plus `barline_tests.cpp`,
`clef_courtesy_tests.cpp`, `expression_tests.cpp`, `lyrics_tests.cpp`, `system_dividers_tests.cpp`
(all call `undoChangeProperty`). No Inspector unit tests exist (`git ls-files src/inspector | grep -i test` is empty).

**Scenarios.**
- GEN-SP-01 set PLACEMENT=below on a dynamic in the master; part copy follows; one undo reverts both.
- GEN-SP-02 same edit on the part's copy; master unchanged; part's APPEARANCE/POSITION link flag cleared.
- GEN-SP-03 OFFSET {x:1,y:-2} on a note lands on its chord; on a hairpin with segment 0.
- GEN-SP-04 VISIBLE=false on a note hides note, dots and accidental (undoChangeVisible route).
- GEN-SP-05 COLOR on a slur; read back as `#RRGGBB`.
- GEN-SP-06 BEAM_MODE=begin16 on a quarter note → E_NO_EFFECT, score untouched.
- GEN-SP-07 unknown name, wrong type, out-of-range enum, refused Pid (TICK) → each its error code, no undo entry.
- GEN-SP-08 null value resets a styled property; flag back to STYLED.
- GEN-SP-09 TEXT_STYLE change on staff text; font Pids follow the new style.
- GEN-SP-10 batch of 20 set_property calls → one undo entry.

**Open questions.**
1. OFFSET on spanners needs a laid-out spanner (segments exist only after layout, notes-G8).
   Does the core lay out between batch steps, or is segment OFFSET refused for spanners created
   in the same batch?
2. Should set_property on a part element be allowed at all in v1, given that it silently unlinks
   (GG5)? Or require an explicit `scope: "part"` flag?
3. The Inspector notifies `notationChanged` before commit (`aim.cpp:495-496`); the core notifies
   after commit. No consumer was found that depends on the order; not verified at runtime.

### remove  ·  command://notation/remove

**UI entry point.**
`Delete` key / Edit ▸ Delete → action `action://notation/delete` (`nac.cpp:231`) →
`NotationInteraction::deleteSelection()` (`ni.cpp:5427-5451`): `startEdit("Delete")`; if text
editing, deletes text (`ni.cpp:5435-5441`); else `doEndEditElement(); resetGripEdit();
score()->cmdDeleteSelection()` (`ni.cpp:5442-5446`); then `checkAndShowError()` (`ni.cpp:5448`,
GG3) and `apply()`. Cut is the same after a clipboard copy (`nac.cpp:1284-1293`).
The agent must call `Score::cmdDeleteSelection()` (`edit.cpp:4002-4175`) directly, not the wrapper.

For a LIST selection, `cmdDeleteSelection` loops a copy of the selected elements
(`edit.cpp:4014`) and for each:
- refuses the first key signature or an instrument-change key signature with
  `MScore::setError(CANNOT_REMOVE_KEY_SIG)` (`edit.cpp:4080-4086`);
- skips a trill cue note (`edit.cpp:4089-4092`);
- inside an FBox, hides a fret diagram/harmony instead of deleting (`edit.cpp:4094-4101`);
  outside, deleting a fret diagram re-parents its harmony to the segment (`edit.cpp:4102-4108`);
- de-duplicates linked copies and segments of the same spanner (`edit.cpp:4016-4021`, `4117-4146`);
- calls `Score::deleteItem(e)` (`edit.cpp:4136`).
Then `deselectAll()` and reselects a nearby chord/rest (`edit.cpp:4150-4174`).
The guards above live only in `cmdDeleteSelection`; the plugin API's `removeElement` calls
`deleteItem` directly (`src/engraving/api/v1/qmlpluginapi.cpp:374-378`) and skips them.

`Score::deleteItem` (`edit.cpp:2726-3361`) per element type:
| Element | Effect |
|---|---|
| any `generated()` element except BAR_LINE, BRACKET, CLEF, INSTRUMENT_NAME, KEYSIG, MEASURE_NUMBER, SYSTEM_LOCK_INDICATOR, HAMMER_ON_PULL_OFF_TEXT, PLAY_COUNT_TEXT, LYRICSLINE_SEGMENT | nothing (`edit.cpp:2732-2750`) |
| NOTE in a chord with >1 note | note removed; **selects the chord's down note** (`edit.cpp:2820-2825`) |

**Selection set-up.** Build a LIST selection on the edited score containing exactly the resolved
elements: `NotationInteraction::select(elements, SelectType::REPLACE)` (`ni.cpp:971-999`), or the
engraving equivalent `Score::deselectAll()` + `Score::select(elements, SelectType::ADD)`
(`score.cpp:3349-3358`, `3434-3462`). Do **not** use the interaction's `select` with
`SelectType::ADD` and one element: it reads the live keyboard state and toggles the element off if
Ctrl is held (`ni.cpp:1011-1021`). Spanner handles: put `spanner->frontSegment()` in the selection
when segments exist, as the UI does (`ni.cpp:1071-1073`), so the segment branch of `deleteItem`
runs; a bare Spanner falls to the default branch and skips tie jump-point and guitar-bend handling
(`edit.cpp:3207-3224` vs `3357-3359`).
Restore the user's selection afterwards (notes-G5; GG8 restores it on undo).

| Check | Error |
|---|---|

**Post-condition.** Per element, by structural re-walk (never through the EID register, which
can return freed objects): the element is gone from its parent; for NOTE/CHORD a rest of the
same ticks exists at the same tick and track; for voice 2–4 rests the slot holds a gap rest or
nothing; for the "transform" rows (MEASURE_NUMBER, TBox TEXT, PLAY_COUNT_TEXT, NORMAL barline type,
accidental) the documented property changed. `MScore::_error == MS_NO_ERROR` after the call.

**Nested commands.** None in `cmdDeleteSelection`/`deleteItem` for the accepted types (GG2).
`cmdRemoveTimeSig` (refused) is the only `unwind()` reachable.

**Linked parts / excerpts.** `undoRemoveElement` and `removeChordRest` remove all linked copies
(`edit.cpp:7490-7493`, `4632-4648`); `undoAddCR` adds the replacement rest to all linked staves
(notes-G7); `cmdDeleteSelection` avoids double deletion of linked items in the selection
(`edit.cpp:4031-4035`, `4143-4146`). Deleting from a part therefore also deletes in the master.
Measure-level flags are looped over `scoreList()` (`edit.cpp:3032-3049`).

**Crash and corruption risks.**
- `TIMESIG` → `unwind()` of the whole batch (GG3, structure-G3).
- `CANNOT_REMOVE_KEY_SIG` makes the outer `endCmd` roll back the whole batch (GG3).
- Plugin API `removeElement` → `deleteItem` directly: no key-signature guard, no FBox handling,
  no linked de-duplication (`qmlpluginapi.cpp:374-378`).
- Deleting a note selects another note (`edit.cpp:2823`) and `cmdDeleteSelection` reselects
  (`edit.cpp:4150-4174`): user selection must be restored by value, not pointer (notes-G5).
- `deleteItem` on a generated beam frees it directly (`edit.cpp:4655-4658`, GG4).

**Existing upstream tests.**
`barline_tests.cpp:415` (deleteSkipBarlines), `beam_tests.cpp:266` (deleteBeamStemDirection),
`box_tests.cpp:45` (undoRemoveVBox), `chordsymbol_tests.cpp:122` (testClear),
`instrumentchange_tests.cpp:83` (testDelete), `links_tests.cpp:181` (test3LinkedParts_99796),

`selectionrange_tests.cpp:158/196/256/261` (range deletes), `selectionfilter_tests.cpp:320/357`.

**Scenarios.**
- GEN-RM-01 remove the only note of a chord → quarter rest at the same tick; part shows the same.
- GEN-RM-02 remove one note of a triad → dyad remains.
- GEN-RM-03 remove a dynamic, a hairpin (by spanner handle) and a slur in one call → all gone, one undo.
- GEN-RM-04 remove a voice-2 rest → gap rest; voice-1 rest → E_NOT_REMOVABLE, no undo entry.
- GEN-RM-05 remove a tied note's tie (segment route) across a repeat jump point.
- GEN-RM-06 remove the first key signature → E_NOT_REMOVABLE, batch not rolled back.

- GEN-RM-08 remove a tuplet → one rest of the tuplet's length.
- GEN-RM-09 remove a stale handle (element deleted by a previous request) → E_STALE_HANDLE.

**Open questions.**
1. Should `remove` on a voice-1 rest be refused (current proposal) or turned into a no-op
   success? The UI silently does nothing (`edit.cpp:2916`).
2. A spanner created earlier in the same batch has no segments (notes-G8); `remove` on it then

### select  ·  command://notation/select

**UI entry point.**
`INotationInteraction::select(elements, type, staffIndex)` (`src/notation/inotationinteraction.h:77-78`,
`ni.cpp:971-999`): snapshots the old selection, calls `doSelect` (`ni.cpp:1001-1045`), and calls
`notifyAboutSelectionChangedIfNeed()` only if state, elements or range changed (`ni.cpp:994-998`).
`doSelect` ends element/text editing if the new selection requires it (`ni.cpp:1005-1009`),
converts REPLACE to `deselectAll` + ADD (`ni.cpp:1023-1026`), expands a SINGLE key/time signature
to all staves at that segment (`ni.cpp:1028-1042`), then `Score::select` (`ni.cpp:1044`).
Other entry points: `selectAll` (`ni.cpp:1082-1092` → `Score::cmdSelectAll`, `score.cpp:4288`),
`clearSelection` (`ni.cpp:1122-1145`; also aborts a drag with rollback, `ni.cpp:1130-1134`),
`selectionFilter()` (`ni.cpp:1152-1155`).

Engraving: `Score::select` → `doSelect` per element (`score.cpp:3349-3381`):
- SINGLE: `selectSingle` (`score.cpp:3388-3416`) — sets **input state track and segment**
  (`score.cpp:3402-3410`); a MEASURE becomes a RANGE on the covering mmrest (`score.cpp:3396-3398`).
- ADD: `selectAdd` (`score.cpp:3434-3462`) — if the selection is a range, behaves as SINGLE
  (`score.cpp:3438-3441`).
- RANGE: `selectRange` (`score.cpp:3528-3609`) — extends an existing selection, uses
  `coveringMMRestOrThis`/`lastMeasureMM` (layout-dependent, structure-G6) and "select similar"
  heuristics (`score.cpp:3611-3658`).
Range by ticks (no UI action, but the plugin API's `Selection::selectRange` uses it,
`src/engraving/api/v1/selection.cpp:117-146`): `Selection::setRange(startSeg, endSeg, staffStart,
staffEnd)` (`select.cpp:858-875`) or `setRangeTicks` (`select.cpp:885-901`, resolved in
`updateSelectedElements` via `tick2segmentMM`, `select.cpp:690-700`), then
`updateSelectedElements()` (`select.cpp:679`), which applies the selection filter.

**Selection set-up.** This command *is* the selection set-up. Recommended engraving sequence per
form (all on the score of the notation the user is viewing, GG7):
- handles → `NotationInteraction::select(items, SelectType::REPLACE)` (fires the notification;
  safe from the Ctrl check because the type is REPLACE at `ni.cpp:1011`).
- range → `Score::deselectAll()`, `Selection::setRange(…)` with segments from
  `tick2segment` (not MM), `updateSelectedElements()`, then trigger the notification
  (GG7: only through a public interaction method or a commit).
- none → `INotationInteraction::clearSelection()`.

**Arguments.**
```json
{

  "oneOf": [
    { "required": ["handles"], "properties": { "handles": { "type": "array", "minItems": 1, "items": { "$ref": "#/defs/handle" } } } },
    { "required": ["range"], "properties": { "range": {
        "type": "object", "required": ["start", "end", "staves"],

          "start":  { "$ref": "#/defs/position" },
          "end":    { "$ref": "#/defs/position", "description": "exclusive; null = end of score" },
          "staves": { "$ref": "#/defs/staffRange" },
          "voices": { "type": "array", "items": { "type": "integer", "minimum": 1, "maximum": 4 }, "description": "optional, applied through the selection filter" } } } } },
    { "required": ["none"], "properties": { "none": { "const": true } } }
  ]

```

**Validation before mutation.**
| Check | Error |
|---|---|
| handles live; mapped to the viewed score with `findLinkedInScore` (`src/engraving/dom/engravingitem.h:500`) | E_STALE_HANDLE / E_NOT_IN_VIEW |
| range: `staffEnd > staffStart`, `staffEnd <= nstaves()`; `end` after `start` (`select.cpp:860-861` are `assert`s, compiled out in release) | E_RANGE |

state: LIST with exactly the elements, or RANGE with the requested ticks/staves; the
`selectionChanged` notification fired once.

**Nested commands.** None. Selection changes are not undo commands; inside a transaction they are
captured by the macro snapshot (GG8). As a stand-alone request `select` should not open a
transaction at all (nothing to undo; an empty macro would be discarded anyway, notes-G1).

**Linked parts / excerpts.** Selection is per score object (GG7). The visible selection is the
current notation's score; if the user views a part and the handle is a master element, select its
linked copy in the part. Edits made through the master use the master's own selection
(remove's set-up), which is invisible while a part is shown.

**Crash and corruption risks.**
- `Selection::setRange`/`setRangeTicks` only `assert` staff bounds (`select.cpp:860-861`, `887`).
- `NotationInteraction::doSelect` with ADD + one element reads `QGuiApplication::keyboardModifiers()`
  (`ni.cpp:1011`): nondeterministic for an agent.
- `selectSingle` moves the input state (`score.cpp:3402-3410`); after a select the next
  note-input start uses that position (by design).
- `Selection::lock` exists (`src/engraving/dom/select.h:108-110`) but has no callers in 4.7.6
  (only the plugin API reads `lockReason`, `selection.cpp:51`); `clear` and
  `updateSelectedElements` `IF_ASSERT_FAILED` on it (`select.cpp:453-456`, `681-684`).
- Selection filter changes (`notationselectionfilter.cpp:40-67`) persist on the score and
  re-filter a live range; the agent must restore the user's filter after using it.

**Existing upstream tests.**
`selectionfilter_tests.cpp:103-208` (each filter type), `:320`, `:335`, `:357`;
`selectionrange_tests.cpp:82` (selRangeAndSpanners). No tests for `NotationInteraction::select`
(`src/notation/tests` has only mocks).

**Scenarios.**
- GEN-SEL-01 select two dynamics by handle → LIST of 2, Inspector shows dynamics.
- GEN-SEL-02 select bars 5–8, staves 1–2 → RANGE; status bar shows the range.
- GEN-SEL-03 select range with voices [2] → filter applied, user filter restored afterwards.
- GEN-SEL-04 select while viewing a part with a master handle → linked copy selected.
- GEN-SEL-05 select `none` → empty selection.
- GEN-SEL-06 select with stale handle → E_STALE_HANDLE, selection unchanged.

**Open questions.**
1. Should `select` be a separate request (outside any transaction) only, or also allowed as a
   batch step (it then leaves the selection at the end of the batch as the "sensible" final
   selection the assessment asks for)?
2. With multimeasure rests on, `updateSelectedElements` resolves ticks through
   `tick2segmentMM` (`select.cpp:696-699`). Whether a range selection built from underlying
   measures is drawn correctly on mmrests was not verified.
3. When the agent edits the master while a part is displayed, `commitChanges` on the master's
   undo stack notifies the master interaction (`ni.cpp:255-258`). Whether the part notation's
   interaction also receives `stackChanged` (they share one engraving `UndoStack`,
   structure-G4) was not resolved from source.

### cmd  ·  command://notation/cmd

**UI entry point.**
Menu items, shortcuts and toolbar buttons dispatch an action code through
`IActionsDispatcher::dispatch` (`src/framework/actions/internal/actionsdispatcher.cpp:44-131`),
which calls every registered client whose `canReceiveAction` is true (`actionsdispatcher.cpp:104-125`).
`NotationActionController::init` registers the notation codes (`nac.cpp:88-578`);
`canReceiveAction` gates on an open master notation, not the review page, at least one part, and
the per-code enabler (`nac.cpp:580-614`). The registration wrappers add, after the handler,
`seekSelectedElement()` (moves the playback cursor) and, for codes registered with
`PlayMode::PlayNote/PlayChord`, `playSelectedElement()` (plays audio) (`nac.cpp:2464-2481`,
`2529-2573`, `2200-2232`); move-selection codes play as well (`nac.cpp:2445-2462`).
The plugin API's `cmd(s)` is a bare `dispatch` with a 10-entry rename map and no allow-list
(`src/engraving/api/v1/qmlpluginapi.cpp:408-425`).

**Recommendation from the code: do not dispatch.** Dispatching acts on `currentNotation()`
(`nac.cpp:616-619`), i.e. the part the user is viewing rather than the master; runs every client
registered for the code; adds playback seek and audio; and depends on enabler state. Instead,
the registry maps each allow-listed code to the same engraving call the controller reaches,
executed inside the core's transaction with a prepared selection.

**Selection set-up.** Every allow-listed code is selection-driven. Several treat an empty
selection as "whole score" (`cmd.cpp:2748-2751`, `2859-2862`; `score.cpp:874`): the core must
pass an explicit `range` or `handles` and refuse an empty selection unless `scope: "score"` is
given.

**Arguments.**

**Post-condition.** These calls return void and most have no single checkable result. Minimum:
`MScore::_error == MS_NO_ERROR` and the active macro gained children
(`UndoStack::activeCommand()->childCount()` before vs after, `src/engraving/editing/undo.cpp:582-585`);
no new children → E_NO_EFFECT. Per code where cheap: BEAM_MODE values on the selected chord/rests;
TPC values for spell codes; measure USER_STRETCH for reset-stretch.

**Nested commands.** None for the allow-list (checked: no `startCmd/endCmd` in the listed bodies,
GG2 grep). `del-empty-measures` → `deleteMeasures` (`edit.cpp:3367+`) has no nested command.

**Linked parts / excerpts.** All allow-listed calls change properties through `undoChangeProperty`
(GG5) or add/remove through `undo*` helpers. They act on `score()` of the notation they are
called for; resolve against the master (notes-G7, structure-G4), except that
`cmdRemoveEmptyTrailingMeasures` redirects to the master itself (`cmd.cpp:4726`).

**Crash and corruption risks.**
- 4.7.6 fixes a crash from plugin `cmd("add-hairpin")` inside `startCmd/endCmd` (assessment);
  `add-hairpin` enters grip edit (`ni.cpp:5586`) and stays refused.
- "Empty selection means whole score" (`cmd.cpp:2748-2751`, `2859-2862`; `score.cpp:874`): a
  failed selection set-up silently widens the edit to the whole score. The core must assert the
  selection it built before calling.
- Dispatching instead of direct calls would act on the viewed part and play audio (above).
